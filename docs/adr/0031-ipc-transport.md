# ADR-031 — Coordinator-to-Worker IPC Transport

**Status:** Accepted

**Context.** `[ADR-008]` defines three process classes: the UI/coordinator process (Z0) and sandboxed worker processes (Z1). `[ADR-004]` establishes a command/event protocol for shell↔coordinator communication but does not specify the mechanism for coordinator↔worker communication — only that it is an "IPC transport with a shared-memory side channel for bulk pixel data" (`SDS §1.1`). The `protocol` crate (`[ADR-025]`) will define typed message shapes. The actual OS mechanism — how bytes flow between coordinator and worker processes — has not been fixed.

Without this decision the `coordinator`, `worker-main`, and `sandbox` crates cannot be scaffolded: the coordinator spawns workers and must establish a control channel before passing off the file handle and locking the sandbox (`SDS §3.1` steps 2–3); the per-platform sandbox setup must be structured around whatever file descriptors/handles the worker is allowed to inherit.

**Problem statement.** Choose the IPC mechanism for coordinator↔worker control-message exchange satisfying: (a) runs on all three target platforms (Linux, Windows, macOS); (b) compatible with per-platform sandbox constraints — the channel is established before sandbox lockdown so the worker inherits a pre-opened fd/handle and needs only `read`/`write`/`recvmsg`-class syscalls on it; (c) blocking/synchronous — no async runtime in the core (`GR-6`, `[ADR-010]`); (d) ordered and reliable — correlation-ID-tagged messages arrive in order; (e) abstractable behind a trait so platform specifics are invisible to coordinator and worker logic; (f) minimal new dependencies.

**Decision.** Platform-native local IPC behind a `WorkerTransport` trait:

1. **Mechanism.** Unix domain sockets (`AF_UNIX`, `SOCK_STREAM` with the 4-byte length-prefix framing below) on Linux and macOS; Windows named pipes (`\\.\pipe\<per-worker-uuid>`) on Windows. Both provide ordered, reliable, local-only, connection-oriented messaging with no network exposure.

2. **Establishment sequence.** The coordinator creates the socket path/pipe name, listens, spawns the worker, passes the connected fd/HANDLE as an inherited handle before sandbox lockdown, then installs the full sandbox. The worker receives the handle and calls no socket/pipe creation syscall from within the sandbox — the sandboxed syscall filter never needs `socket()` or `CreateNamedPipe()` in its allowlist.

3. **Framing.** A 4-byte little-endian length prefix followed by the serialized message body. The transport layer carries opaque `&[u8]` frames; serialization format is a separate, later decision. Bincode (`[ADR-028]` Tier 2, MIT) is the recommended first implementation — Rust-native, fast, compact — pending profiling evidence.

4. **Shared-memory side channel.** Tile-buffer shmem regions are created by the coordinator before the render request. The descriptor (a handle or fd integer) is passed as a field in the typed control message — not via `SCM_RIGHTS` or `DuplicateHandle`. The worker maps the region, writes the raster, and returns the handle in its `TileReady` reply. This keeps shmem lifecycle explicit and auditable at the coordinator (`SDS §4.2`).

5. **Trait.** A `WorkerTransport` trait in the `protocol` crate:
   - `fn send_frame(&mut self, bytes: &[u8]) -> Result<(), TransportError>`
   - `fn recv_frame(&mut self) -> Result<Vec<u8>, TransportError>`
   
   Platform implementations (`UnixWorkerTransport`, `WindowsWorkerTransport`) live in `sandbox/`. The `coordinator` and `worker-main` crates reference only the trait; no platform-specific IPC types cross the crate boundary.

6. **Threading.** In the worker: the IPC handler thread uses a **timeout-based receive** (not an infinite blocking `recv_frame`) so new frames — including higher-generation tile requests and explicit cancellations — arrive while the rayon pool is busy rasterizing older work. Generation counters are carried in the message payload, not the transport (`SDS §5.3`); a rayon task whose request's generation has been superseded discards its result and returns without sending a reply, so the IPC thread is never held waiting for a specific generation. In the coordinator: each worker's transport runs on a dedicated receive thread posting messages to the coordinator actor's inbox (`SDS §7.2`). **Crash detection:** EOF on `recv_frame` (socket closure on Linux/macOS; `ERROR_BROKEN_PIPE` on Windows) is the primary signal that a worker process has died; the receive thread catches this condition and posts a `WorkerDied` internal event to the coordinator actor, triggering the `SDS §10.1` recovery sequence. No out-of-band heartbeat or timer is required — the OS closes the socket when the process exits, making crash detection reliable by construction.

**Alternatives considered.** (a) **OS pipes (stdin/stdout):** simpler setup but message-boundary preservation requires the same length-prefix framing; conflicts with worker standard-I/O reuse; `SOCK_STREAM` or named pipes are equally simple once framing is included. Rejected. (b) **`ipc-channel` crate (Servo):** a proven multi-process Rust IPC library, but it would be a Tier-1-equivalent dependency (`[ADR-028]`) requiring adoption note and exit-seam analysis; the platform-native approach is fully contained in `sandbox/` with no new Tier-1 crate. Reconsidered if the abstraction proves inadequate. (c) **Async transport (tokio, async-std):** violates `GR-6`. Rejected. (d) **Shared-memory-only with flag/event signaling:** viable for tile data, but a control channel is needed regardless for lifecycle, error, and cancellation messages; shmem-only would duplicate the control path. Rejected as the sole mechanism. (e) **Platform buses (D-Bus / XPC / COM):** heavyweight, platform-specific, not available inside sandboxed contexts without special entitlements. Rejected.

**Trade-offs.** Two platform implementations to maintain — POSIX sockets (Linux/macOS) and Windows named pipes. `SOCK_SEQPACKET` is unavailable on macOS (only `SOCK_STREAM`); the length-prefix framing already handles message-boundary reassembly so this is a minor difference in the socket option, not an architectural one. Windows named pipe security descriptors must explicitly grant the worker's AppContainer SID access — standard but requires correct plumbing in the broker.

**Consequences.** `WorkerTransport` is the testable seam: coordinator/worker interaction can be unit-tested with an in-process stub transport, enabling the deterministic inbox-replay technique described in `SDS §7.5` and `[ADR-022]`. Platform IPC code is isolated to `sandbox/` behind `#[cfg(target_os)]` blocks; no platform types appear in `coordinator` or `worker-main`. The framing layer is independent of the serialization format, so serialization can be changed without touching the transport. A closed socket or broken-pipe error on the coordinator's receive thread is the crash-detection primitive relied on by the `SDS §10.1` recovery path; this guarantee is structural — the OS closes the peer socket on process exit, so no heartbeat or watchdog timer is needed for basic liveness. **Wire-format independence:** the IPC control-message serialization (bincode or successor) and the WIT component-model interface used by plugins (`[ADR-015]`) are deliberately separate formats; plugin code never sees raw IPC bytes, so changes to the internal wire format are invisible to the plugin API surface, and vice versa.

**Future considerations.** If profiling shows cancellation-frame latency matters on high-frequency viewport-change paths, a separate lightweight "cancel" channel (a single-byte signal socket) can be added alongside the main transport without changing the `WorkerTransport` API. The serialization format for IPC message bodies (bincode vs. postcard vs. alternatives) is an open implementation decision deferred to M0 implementation; it does not affect the `WorkerTransport` API. Any format choice that carries wire-compatibility implications across versions will require its own ADR.

---

*Accepted. Scaffolding of `coordinator`, `worker-main`, `sandbox`, and `shell/chrome/` may proceed.*
