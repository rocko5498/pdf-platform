| **M0/M2** | PDFium calls were not serialized | **Fixed 2026-08-22 — silent text corruption under concurrency** | `PdfiumEngine` carried `unsafe impl Send + Sync` and a doc comment promising "multiple tiles can be rasterized concurrently". PDFium is not thread-safe. Two tests in one binary were enough to prove it: Windows extracted "Hello extraction" as **"Helo xtracion"** — characters silently dropped from a document's text — and Ubuntu aborted with `free(): invalid pointer`. Every entry point (both constructors, `rasterize`, `extract_page`, `outline`, `layers`, `attachments`, `page_meta`) now serializes on one process-wide lock, and the document is destroyed **inside** that lock: `PdfDocument::drop` calls into PDFium too, and field destruction runs after any guard a method held, so a document going out of scope on one thread raced an extraction on another. Regression test extracts from 8 threads and requires identical text. **Ceiling stated:** one global lock, so no two PDFium calls overlap anywhere in a process; the worker is single-writer per document (SDS §7.4) so this costs nothing today, and a per-document lock is the upgrade if parallel utility jobs ever need it [ADR-005, ADR-027, CR-4, PRIN-1, GR-8] |
| **M2** | Find did not use the normalizer, and panicked on multi-byte text | **Fixed 2026-08-22 — the product searched with the wrong matcher** | The first end-to-end search test over a real document found two defects. `PageTextModel::find_all` sliced each line by **byte** index while naming the result `char_offset`, and advanced `start + 1` byte, so the next slice landed inside a codepoint and **panicked** — reachable from any document with non-ASCII text and a search box (PRIN-1). Its offsets were byte values in fields named for characters, so selection and highlight geometry were wrong on any non-ASCII line. Worse, it is **literal substring matching**: the product's search path called it rather than `search::find_all`, so none of the normalization FR-SRCH-1 requires was applied — typing `cooperate` did not find `co<U+00AD>operate` on the page, while the `search` crate's own tests passed because they run over hand-written models. Matching now runs in the coordinator, which is the layer that can see both crates (`search` depends on `text-extract`, so the service cannot call it), and the raw matcher is char-correct for callers that want literal text. `coordinator/tests/search_e2e.rs` drives the whole chain — extraction, normalization, match location, selection geometry — including a negative case, a ligature, a soft hyphen, and an unreliable page whose matches must arrive flagged [FR-SRCH-1, FR-SRCH-2, FR-SRCH-5, ADR-019, PRIN-1, PRIN-6] |

| **M4** | XFDF import/export | **Round-trip was self-consistent and wrong; fixed 2026-08-23** | The exported `rect` attribute carried `x, y, width, height`, and the importer read the third and fourth numbers back as width and height. Moves are counted separately from content changes so a relocation does not inflate the edit count. The case it exists for is proven end to end: two documents with byte-identical extracted text where one has a black box drawn over a clause used to compare as *"Documents are identical (text content)"* and now report `appearance: 1.65% of pixels differ (max channel delta 255)`. A page whose size changed counts every pixel outside the overlap as changed, so a grown page cannot be flattered by measuring only the shared area, and a failed render is an error rather than a clean bill of health. **Not claimed:** this is a measurement, not perceptual judgement — no SSIM, no "looks the same to a human" model — and the 8/255 tolerance for anti-aliasing noise is chosen, not corpus-calibrated. Rendering is at 0.5x, which answers "did this page change" rather than grading fidelity; that is corpus-diff's job [FR-CMP-1, FR-CMP-2, FR-CMP-3, US-LAW-3, ADR-019, GR-4, GR-7, GR-8, PRIN-6] |
| **M2** | Extraction reliability flag was inert | **Real detection added 2026-07-27** | `PdfiumEngine::extract_page` returned `reliable: true` unconditionally (`// TODO: detect unreliable ToUnicode maps`), so no page was ever flagged and the ADR-019 §4 honesty path — flag unreliable text rather than let it be "silently searched wrong", and offer OCR instead — could never fire. FR-SRCH-5 requires exactly that flagging.
